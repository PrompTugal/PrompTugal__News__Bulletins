This page explains how: the pipeline, the page that draws each frame, the software 3D renderer we switched to, how four browsers share the work, the voice, a bug we found and fixed on the way, and what it all cost in time and money.

1. What you are watching

Each frame is one web page, 1280 x 720, in two halves. The left half is a set of slides drawn with HTML and SVG (slides.js); every number on them comes from script.json, which names its source. The right half is the twelve version 2 presenters, built and animated in 3D with three.js 0.160.1 by the engine in /lab/presenters/v2-claude/ (also published as the presenters library). Each scene is spoken by one presenter, whose name tag turns yellow; all twelve mouths follow the voice, and the others look at the speaker. The camera cuts to the speaker and eases back to the wide shot.

2. The pipeline

  1. Script. Eleven scenes, fixed in bulletins/explainer-v2.mjs. Numbers are spoken in words and shown in figures on the slides, so the word-for-word check on the voice stays simple.
  2. Voice. OpenRouter's openai/gpt-audio-mini, stock voice "alloy", one take per scene. The model returns the audio and its own transcript; the transcript must match the script word for word or the take is refused (up to three takes a scene, or nothing is published). This time: 11 takes for 11 scenes, all matched first time, 0.008 USD, 19.88 s.
  3. Timeline. Each scene runs for exactly its take's length, with 0.45 s between scenes. The voice's loudness, measured 30 times a second, picks a mouth shape for every frame (Rhubarb's letters A to H and X). That is an approximation of lip-sync, not phonemes.
  4. Direction. cast.json says who speaks when, what the others do (wave, nod, think, flinch, celebrate and so on, from the engine's move list) and where the camera is. script.json drives the slides.
  5. Frames. bulletins/frames.mjs draws every frame in headed Chromium on a virtual screen, with the 3D half rendered by Mesa llvmpipe, in 4 browsers at once (sections 3 to 5).
  6. Video. ffmpeg joins the 3,715 PNG frames and the voice: H.264 (libx264, CRF 21, yuv420p) and AAC, with the index at the front so it starts playing at once.

3. Inside one frame: every frame is a function of t

split.html holds the two halves as iframes and exposes renderSplit(t), which calls renderAt(t) on both. Neither half keeps anything from the frame before: the slides rebuild their whole markup from t, and the engine computes every pose from t. Swinging parts (antennas, ties, tufts, keys, the cube's jelly) need memory, so they are integrated on one fixed grid of 1/120 s from rest at t = 0, with a checkpoint every second; any t visits the same grid points with the same arithmetic.

That is what makes the speed-up possible: frames can be drawn in any order, by any number of browsers, and the same t always gives the same picture.

4. Why the frames were slow, and the renderer we switched to

With no GPU, Chromium draws WebGL in software. Measured on this machine (one browser, median of 8 frames):

What was measuredSwiftShader (before)Mesa llvmpipe (now)
Screenshot, nothing changed since the last one33 ms32 ms
Screenshot after drawing a new frame of the 3D half638 ms233 ms
JavaScript time to set up the 3D frame10 ms10 ms

The screenshot itself is cheap. It waits for Chromium's GPU process to draw the scene, and the scene is heavy for software: about 650 draw calls and 645,000 triangles a frame with 4x edge smoothing (MSAA), counted with three.js's renderer.info. Halving the resolution saved little, because the cost is per triangle, not per pixel.

Chromium's own software renderer is SwiftShader. Mesa's llvmpipe is a software OpenGL driver that compiles its shaders with LLVM into 256-bit vector code and uses every core. Chromium uses it only with a display, so frames.mjs:

  1. starts its own Xvfb (a virtual X screen) on a free display number;
  2. launches Chromium headed on that display with --use-gl=angle --use-angle=gl --ignore-gpu-blocklist, so WebGL goes through ANGLE to OpenGL, which is llvmpipe;
  3. asks the page which renderer WebGL reports (WEBGL_debug_renderer_info). This render reported: ANGLE (Mesa, llvmpipe (LLVM 20.1.2 256 bits), OpenGL 4.5);
  4. if Xvfb or Mesa is missing, or the page reports anything else, falls back to headless SwiftShader and says so in the stats (this render did not fall back).

5. Four browsers, one video

The 3,715 frames are split into 4 contiguous ranges, one per browser and one browser per CPU core. Each browser loads split.html, waits until both halves are ready, then for each frame runs renderSplit(t) and takes a Chrome DevTools screenshot (Page.captureScreenshot, PNG). Because every frame is a function of t, the split does not change the picture. ffmpeg then reads the PNGs in order.

Why not record the screen while the video plays?

It would take exactly the video's length, but only if the page can draw 30 frames a second. Playing live on Xvfb, it drew 1.9 frames a second with SwiftShader and 5.6 with llvmpipe. A 10 s screen recording (ffmpeg x11grab) held 300 frames but only 51 different pictures, so movement jumps and mouths miss the voice. Recording also loses determinism and cannot use more than one browser. With a GPU it would likely win; we have none.

8. A bug found on the way: frames that remembered

Renders split differently across browsers gave slightly different frames: 704 of 939 frames differed (46 to 57 dB, invisible, but not the same bytes). There were two causes:

  • Springs. A swinging part added its lag to its joint's angle. When the pose code did not set that joint outright every frame (an antenna, a tuft, a key), the lag of the previous frame stayed in the angle. The engine (engine/rig.js) now puts every spring joint back to its built rotation and scale before applying the pose.
  • Name tags. On the showcase page the tags had will-change: transform, so Chromium rasterised their text once, at the sub-pixel position where each tag first appeared, and moved the bitmap after that. Removed.

The determinism test (tools/determinism.mjs) now also draws the same t after a long history and requires byte-identical PNGs. It failed before the fix and passes after. The fix is in presenters library 0.1.1. One residue: in headed Chromium the version 1 stage's text can differ by at most 2 of 255 levels between histories (Chromium's compositor, about 70 dB); the 3D half is byte-identical.

10. Make it yourself

# from the repository root (PrompTugal/PrompTugal__News__Bulletins), with Node, Playwright's Chromium, ffmpeg, Xvfb and Mesa
OPEN_ROUTER_KEY=... BULLETINS_AGENT=d node bulletins/explainer-v2.mjs     # voice, then frames: about 0.01 USD
BULLETINS_AGENT=d node bulletins/explainer-v2.mjs --reuse                 # frames only, from the saved voice: no cost
node bulletins/explainer-v2.mjs --page-only                               # this page, from stats.json
node src/lab/presenters/v2-claude/tools/determinism.mjs 960 540           # the determinism test

Options: --workers N (default: the number of CPU cores), --fps 30, --renderer auto|llvmpipe|swiftshader. The study's tools and raw results are in docs/research/video-render-speed/.
